The committed scripts in `6b09ac9c` and `30cbada0` do not measure the same full Goose coding loop as the latest 12-trial comparison. Some earlier comparative speedup figures are literal constants. Other measurements time JavaScript helpers or direct Gemini requests. This explains how a script launched from Goose could print a speedup without demonstrating a faster Goose task. The user's exact saved earlier run has not yet been identified; these findings apply to the verified committed scripts below.

Their presence alone does not prove that numbers were invented or that the user's earlier run was invalid. The latest candidate's regression remains real within the observed sample: 668.598 seconds versus 515.388 for default Goose, or **29.7% more elapsed time**. Equivalently, default took **22.9% less time**, not 29.7% less. Candidate requests carried 60.1% more accumulated input tokens, checks were repeated, and the large task used 14 separate guarded edit calls. AST/LSP were not selected, so the result is not a measurement of their execution cost. Integration in Rust does not automatically reduce model work. Batching and receipt changes were an optimization hypothesis that this screen did not validate.

The reliability claim also needs limits. The old helper had specific defects: a dry run returned `verified:true`, and a file could change while the helper awaited the safety service before writing without a fresh preimage check. That supports identifying defects; it does not support calling the entire old Goose build unreliable. The latest comparison produced 12 correct code outputs, with 11 clean completions because the previous native build hit the model-request budget on its large task. There is no demonstrated general reliability improvement. The final audit corrected an overly broad completion classification, retaining the raw result and marking the exhausted comparison invalid for successful-completion timing.
