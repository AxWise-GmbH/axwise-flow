The Sparsity Nexus: From Judy Arrays to Routed LLM Memory

What stops me from downloading a quantized 27B model, setting its context to one million tokens, and running it on an ordinary laptop? I chose the fanless 24 GB M4 MacBook Air because it makes that consumer question brutally concrete. The 2026 evidence supports the working-set thesis; it does not yet prove the MacBook result or that Judy arrays are the winning index.

Published June 11, 2025 • Major thesis update June 2026 • Updated August 31, 2026 • 26 min read
Defensible

Query-aware routing can make long-context inference operate on a small active KV working set in evaluated systems.

Plausible, untested

A Judy-style adaptive radix directory may be useful over sparse semantic codes, KV block IDs, and memory-tier metadata.

Benchmark target

Context-invariant decode on a fanless 24 GB M4 Air; 11–12 accepted tok/s remains the aspirational stretch target.

The consumer question

Why I chose the 24 GB M4 MacBook Air

I chose this machine precisely because it is the wrong machine for a dense one-million-token KV cache. There is no separate GPU memory, no 145 GB host-RAM safety net, and no fan. There is one CPU/GPU memory pool, a local SSD, and just enough capacity to hold a heavily quantized 27B model plus a small active context.

That makes it a useful scientific instrument rather than a convenient demo platform. If logical context can be decoupled from resident context here, the mechanism is doing real work. If it cannot, the failure modes—capacity, bandwidth, cold-tier traffic, quality, or thermals—should be visible and measurable.

24 GB

Total unified memory for macOS, weights, runtime, recurrent state, index, and hot KV—not 24 GB reserved for the model.

120 GB/s

Base-M4 memory bandwidth. Unified memory removes PCIe copies, but CPU, GPU, model weights, and KV compete for the same pool.

Fanless

A short burst is not the benchmark. Long prompt ingestion and sustained decode must survive thermal steady state.

Local SSD

A possible cold KV tier, but every cache miss becomes latency, traffic, and endurance that the benchmark must expose.

Six ordinary questions, with systems answers

“The model file is only about 13–16 GB. Why does 24 GB not solve it?”

Because weights are only one resident. KV state, recurrent state, scratch buffers, the runtime, and macOS need the same memory.

“Why not just set the context window to 1M?”

A configuration permits positions; it does not make the KV payload fit, the prompt cheap to ingest, or retrieval accurate at that distance.

“Does unified memory remove the bottleneck?”

It removes a device/host copy boundary. It does not create capacity or bandwidth, and it can increase contention for the one shared fabric.

“Does 1M context mean an instant 1M-token prompt?”

No. Addressability, prompt ingestion time, time to first token, and decode speed are four different measurements.

“Why not start with a 9B model?”

We should. Smaller hybrid models are controls. The 27B case is valuable because its weights deliberately leave almost no room for dense long-context state.

“Where could Judy actually help?”

After a semantic router creates sparse codes: mapping variable-length prefixes to KV block IDs, tier locations, reuse statistics, and fallback metadata.

Platform facts come from Apple’s M4 MacBook Air specifications, fanless-design announcement, and Metal unified-memory documentation.

The revised argument

The thesis aged better than the implementation claim

The interesting part was never the Judy container alone. It was the possibility that an LLM could discover a small working set first, place that working set on the best available hardware, and perform expensive computation only there.

The original whitepaper was deliberately broader. It contrasted deterministic Judy lookup with probabilistic attention and proposed three branches: tree-based positional encodings, a Judy-indexed KV cache, and Judy-masked attention. The June 2026 update then added compression and related sparse systems. This article follows the most testable descendant—the KV branch—without erasing the other two from the research history.

In its strongest defensible form, the thesis is this: long-context inference should separate addressable memory from active attention. A query-conditioned router promotes a small set of relevant KV pages through a memory hierarchy; exact attention then runs on that working set.

AI scaling is increasingly about finding less, moving less, and computing less—not only multiplying the same matrices faster.

This is where it becomes more interesting

Quantization

How small can each parameter or KV value become without unacceptable quality loss?

Parameter sparsity

How little of the model must be active for this token?

Context sparsity

How little of the remembered context must be active for this query?

instantaneous cost ≈ f(active parameters, active memory)

The goal is to weaken the dependence on total parameters and total addressable context—not to pretend those totals disappear.

KTransformers: parameter working set

A Mixture-of-Experts model already has a router. KTransformers exploits that signal to coordinate CPU and GPU placement.

all experts → routed experts → compute

Sparsity Nexus: memory working set

Attention routing has the harder job: it must predict which historical tokens matter before exact attention scores them.

all KV → retrieved KV → exact attention

KTransformers is therefore both analogy and related implementation—not proof that a Judy index solves KV relevance.

Correcting the complexity story

“Quadratic attention” needs one qualification

Dense prefill across N prompt tokens performs O(N²) attention work. During KV-cached autoregressive decoding, each new token ordinarily scans O(N) historical keys and values, while KV memory itself grows O(N). The proposed system is mainly aimed at that repeated decode-time scan and its memory traffic.

Tdecode = Tmodel + Troute(N) + Tfetch(k) + Tattention(k), where k ≪ N

A routed design does not automatically turn attention into O(log N). A tree lookup may be cheap, but candidate generation, enumeration, transfer, exact attention, and fallback still depend on k and on the routing method. It wins only when those costs together are lower than scanning all N entries and omitted information does not change the answer.

Illustrative work units, not measured latency. The routed curve assumes a fixed 12,288-token candidate budget plus a small index term. Real routing cost, bandwidth, and candidate growth must be measured.

The narrower implementation hypothesis

Where Judy arrays could actually fit

A Judy array does not understand semantic relevance. It maps a discrete key to a value. Attention begins with learned continuous vectors, so a semantic projection must come first: LSH, product quantization, a learned indexer, coarse attention, or a hybrid. Judy can be the directory; it cannot be the semantic oracle.

Soft lookup: attention

Query-dependent similarity over learned vectors. It discovers relevance but normally pays to inspect a large KV region.

  • Input: continuous query/key vectors
  • Strength: learned, contextual relevance
  • Cost: dense memory movement at long N

Hard lookup: Judy-style directory

Exact traversal over integer or byte-string keys in an adaptive radix structure.

  • Input: discrete code or code prefix
  • Strength: sparse key spaces and updates
  • Cost: irregular traversal and postings

A plausible hybrid pipeline

Keep a protected core

System instructions, attention sinks, structural anchors, and a recent-token window remain hot.

Project the query into discrete routes

LSH, PQ, learned micro-block scores, or coarse attention produces codes and candidate code prefixes.

Resolve candidates and residency

A Judy-style directory maps sparse codes to KV block IDs, postings, and hot/warm/cold locations.

Refine, fetch, and attend exactly

A compact scorer reranks candidates; the accelerator fetches the final K/V blocks and performs exact attention over them.

Widen when confidence is low

Expand from 8K to 32K or 128K candidates, or fall back to a denser path. Sparsity becomes a quality–cost decision rather than a fixed mask.

What remains genuinely novel—and genuinely unproven

This audit found no primary-source project using Judy arrays specifically for LLM attention or KV retrieval. The testable contribution is therefore narrow: whether a Judy-style directory beats hash tables, adaptive radix trees, inverted lists, sorted arrays, or GPU-native structures for code-to-block and tier metadata. The broader architecture survives even if Judy loses.

Related work and open source

2026 update: attention is becoming a working-set problem

The field has not converged on Judy arrays—or even on radix trees as a universal answer. It has produced multiple systems with the broader pipeline: select candidates cheaply, move or reconstruct a small KV working set, and reserve expensive attention for that set.

Several of the strongest precedents predate the original June 2025 article. This update cites that prior art explicitly. The article is best defended as a systems synthesis and a Judy-specific hypothesis, not as a claim to have invented sparse attention or KV retrieval.

Closest 2026 match

ParisKV makes the pipeline concrete

ParisKV uses collision-based candidate retrieval, 4-bit approximate inner-product reranking, full KV in pinned CPU memory, and on-demand fetching of only selected K/V pairs through UVA. Its ICML 2026 paper reports million-token scaling and up to 2.8× higher peak decode throughput across batch-size sweeps within full attention’s runnable 64K–256K range.

That is startlingly close to the proposed working-set pipeline. It is not evidence for Judy or Apple Silicon: ParisKV uses GPU-native codebook/collision structures and CUDA. Read the paper.

Direct KV routing and retrieval

Direct precedent

RetrievalAttention / RetroInfer

Treats the KV cache as vector storage and coordinates attention-aware retrieval across CPU and GPU. The repository’s current main implementation presents the newer RetroInfer system.

Original paper
Direct precedent

PQCache

Encodes keys with product quantization, performs approximate maximum-inner-product search, then fetches selected full KV. This is close to the semantic stage a radix directory needs.

SIGMOD 2025 paper
Direct precedent

Quest

Stores min/max summaries for KV pages and uses the current query to select top-K pages. The authors report up to 7.03× self-attention and 2.23× end-to-end speedups in their setup.

ICML 2024 paper
Direct precedent

MagicPIG

Uses CPU-resident LSH tables and sparse CPU attention. Its discrete buckets are a close analogy to the proposed code-to-postings layer, though diffuse attention is a risk.

ICLR 2025 paper
Hierarchical search

HiP / InfiniteHiP

Uses hierarchical pruning and host KV offload. InfiniteHiP reports three-million-token operation on one L40S 48 GB GPU plus large host memory; it is structurally close, but CUDA/Triton and not Judy-based.

InfiniteHiP paper
Selective reconstruction

ShadowKV

Keeps low-rank key information resident, offloads the value cache, and reconstructs a minimal sparse KV set on demand. This supports selective residency, not Judy specifically.

Routing moves into model architecture

Strong 2026 evidence

Qwen QSA

A compressed per-layer micro-block indexer selects important regions. Qwen reports up to 7.6× prefill-kernel and 4.9× decode-kernel speedups at 1M. Official explanation. QSA belongs to Flash-Next, not Qwen3.8-27B.

Learned router

SeerAttention

Learns block-level attention gates through lightweight self-distillation. It adapts a pretrained model, but additional gate training is required.

MoE-style attention

MoBA

Applies MoE-style top-K routing to context blocks. It strongly supports the analogy, but the project explicitly requires continued training for existing models.

Adjacent systems: supportive, but not the same claim

Heterogeneous compute

KTransformers

Validates heterogeneous working sets and now includes CPU sparse attention. Its documented 1M InternLM result uses a 24 GB GPU plus about 145 GB of host KV memory—not a 24 GB total-memory laptop. Details.

Prefix reuse and tiers

SGLang RadixAttention / HiCache

RadixAttention shares exact prompt prefixes across requests; HiCache extends placement through GPU, host, and storage tiers. Neither finds relevant tokens inside one sequence.

Orthogonal compression

TurboQuant

Compresses KV values to roughly three bits in evaluated models and tasks. It makes each item smaller; routing reduces how many items are touched. The approaches are complementary.

Concrete case study

Qwen3.8-27B, one million tokens, and a 24 GB M4 Air

Could a fanless 24 GB M4 MacBook Air run a quantized Qwen3.8-27B with a one-million-token addressable context? The weight side is plausible. The full dense KV side is not. That distinction is precisely where routed memory becomes useful.

First, untangle two similarly named Qwen releases

There is no single model called “Qwen3.8 Next 27B.” Qwen3.8-27B is the dense-parameter, hybrid-attention 27B retrofit target used for the laptop hypothesis. It does not contain QSA. Qwen3.8-Flash-Next is a separate architecture: 125B main parameters plus 51B deterministic n-gram embedding parameters, with 6B main parameters active per token and Query-Selective Attention.

Flash-Next is an architectural control showing that selection can move inside the model. Its QSA arithmetic does not prove selective KV residency for 27B, and its published kernel speedups are not MacBook measurements.

The retrofit target’s architecture matters

The official Qwen3.8-27B model card describes 64 layers arranged as sixteen groups of three Gated DeltaNet layers plus one global Gated Attention layer. Those 16 attention layers use four KV heads of dimension 256. The model is native to 262,144 tokens and extensible with YaRN to one million; extension is not guaranteed task quality at that length. The release artifacts and implementation notes are also in the official Qwen3.8 repository.

16 layers × 2 (K,V) × 4 KV heads × 256 dimensions × 2 BF16 bytes = 65,536 bytes/token

The proposed router has three distinct budgets: kc coarse candidates from the compact index, kf full KV vectors fetched or promoted, and ka tokens that receive exact attention. The hot-cache reuse ratio h determines how often kf can be served without touching SSD or compressed cold memory. Hiding these four values would hide the mechanism.

What will actually stop me?

1 · Weight capacity

A 3-bit 27B distribution may fit, but macOS, Metal workspaces, recurrent state, and the index need real headroom. Loading is not the same as running without swap.

2 · KV capacity

Dense BF16 KV is about 61 GiB at 1M. Even ideal 4-bit KV is about 15.3 GiB before scales and metadata—too much beside the weights.

3 · Decode bandwidth

The base M4 must stream quantized weights and useful KV through 120 GB/s shared bandwidth. Capacity alone says nothing about tokens per second.

4 · Cold-tier traffic

SSD makes a large logical store possible, but random misses, decompression, page faults, and write amplification can erase the savings.

5 · Prompt ingestion

One million addressable tokens do not appear for free. Prefill time, index construction, first-token latency, and reusable cache creation need separate reporting.

6 · Routing quality

A tiny active set helps only if it retains the decisive token. Multi-hop and diffuse-attention tasks may force budget widening or dense fallback.

7 · Runtime and thermals

The fanless Air must sustain performance after a long prefill and extended decode. A five-second burst, a Pro/Max result, or an accepted-token rate inflated by unreported speculation is not this experiment.

The honest verdict on 11–12 tok/s

It is an aspirational research target for this specific Air, not a result for every “M4 Mac.” A base M4 has 120 GB/s memory bandwidth, while M4 Pro has 273 GB/s. Using the 13.1 GB GGUF file payload as a proxy gives an ideal backbone-weight-streaming bound near 9.2 passes/s—before dequantization, KV access, routing, runtime, or thermal overhead. It is not a measured Metal roofline.

Therefore 11–12 output tok/s is aggressive on base M4. Output rate can exceed backbone passes/s only through verified multi-token/speculative acceptance; backend support, acceptance rate, and the separate MTP artifact must be counted. It is more plausible on M4 Pro. See Apple’s M4 MacBook Air specifications and M4 Pro bandwidth.

Fetching a completely new 12,288-token BF16 working set every output token would move 0.75 GiB per step—about 8.25 GiB/s at 11 tok/s. Strong block reuse, compressed transfers, prefetch, and overlap are mandatory. Prefill and time-to-first-token must be reported separately from steady-state decode.

“99% quality” must become a definition

Aggressive Unsloth/GGUF quantization can preserve much of the model’s capability, but it does not establish a universal “99%.” KV routing adds a separate approximation: the one omitted token may contain the fact needed several reasoning steps later.

Task score: no more than 1 absolute percentage point below the same dense, quantized reference on declared RULER and LongBench tasks.
Language modeling: less than 1% relative perplexity increase on named corpora.
Router diagnostic: at least 99% attention-mass recall where a dense reference can be inspected.
Robustness: multi-hop, multi-key, adversarial needle, code, and long generation tests with fallback rates reported.

Consumer model guide

Easier open-weight controls under 30B

The scientifically sensible path does not begin with the hardest 27B configuration. It begins with smaller controls that isolate weight pressure, attention architecture, and routing quality. The models below are practical candidates, not interchangeable claims of “99% of 27B quality.” Capability depends on task, quantization, prompt, and benchmark.

By 2026, model builders already attack long-context memory structurally: Qwen uses recurrent DeltaNet layers, Granite uses a Mamba hybrid, while Gemma and gpt-oss keep much of attention local. A Judy-inspired KV directory would therefore sit one layer deeper: representing and retrieving the remaining long-lived attention state by relevance instead of storing every K/V equally.

Recommended experimental ladder

Start with Granite to validate the memory tiers and index; move to Qwen3.5-9B for a meaningful 1M routing test; use Ministral as an all-global KV stress control; then attempt Qwen3.8-27B only after the smaller systems meet identical quality and telemetry gates. gpt-oss and Gemma are architectural side controls.

Make the thesis falsifiable

The experiment that would actually defend it

The interesting question is no longer whether a quantized 27B model can load on a Mac. It is whether the amount of context it can accurately address can grow much faster than its resident KV memory and per-token attention work.

1. Freeze the baseline

Same model, same quant, same prompts

Freeze the fanless 24 GB M4 Air, macOS version, runtime commit, exact GGUF, Metal settings, YaRN configuration, KV precision, power state, ambient temperature, and MTP configuration. Use a dense reference on larger hardware when 1M cannot fit.

2. Sweep context and budget

Find the quality–working-set frontier

Test 32K, 128K, 262K, 512K, and 1M logical contexts with 2K, 8K, 12K, and 32K retrieval budgets plus adaptive widening.

3. Measure the whole system

Do not hide routing or I/O

Report prompt ingestion, TTFT, p50/p95 decode latency, raw model passes/s, accepted tokens/s, peak unified memory, swap, cold-KV size, bytes fetched, SSD reads, kc, kf, ka, reuse h, index updates, and fallback rate.

4. Isolate Judy

The directory must earn its place

Hold the semantic router constant and compare Judy with a hash table, adaptive radix tree, sorted flat postings, IVF/PQ lists, and a GPU-friendly layout. Measure end-to-end decode, not lookup latency alone.

Proposed success criterion

The primary speed gate is context invariance: after thermal steady state, 1M logical-context decode must retain at least 80% of the same Air’s 32K decode rate, stay below a declared resident-memory ceiling without swap, and meet the quality gates across retrieval, reasoning, code, and long generation.

The 11–12 accepted tok/s figure remains a stretch goal that may require multi-token prediction or speculation. Report raw model passes/s beside accepted tok/s. Until reproduced, both belong under “target,” not “result.”

Claim status after the audit

Evidence for the broader thesis

Claim Status Reason
Long-context decode can use a query-dependent KV working set. Supported direction ParisKV, RetrievalAttention, PQCache, Quest, MagicPIG, HiP, and others demonstrate variants.
Heterogeneous placement can make large addressable state practical. Supported direction KTransformers, ParisKV, ShadowKV, InfiniGen, and hierarchical caches provide evidence.
A Judy-style directory is the best KV index. Open hypothesis No audited project establishes it; comparative benchmarks are required.
Qwen3.8-27B can address 1M tokens at 11–12 accepted tok/s on a fanless 24 GB M4 Air. Unverified target The memory arithmetic motivates routing, but no reproduced Apple Silicon result proves capacity, speed, and quality together.
LLM memory can eventually be virtualized around active working sets. Research thesis Many components exist; general quality, latency, and fallback remain unresolved.

The revised thesis is narrower than “Judy arrays solve attention,” but it is also stronger. Future inference systems may virtualize both parameters and context: enormous state remains addressable, while only a query-dependent working set becomes active.

Quantization reduces the physical size of that state. Expert routing reduces active parameter work. KV routing attempts to reduce active memory and attention work. Accelerator memory can then become a cache for the current intelligence working set rather than the place where all addressable state must live.

Existing systems now demonstrate important pieces. The Judy choice, difficult-task recall, and fanless 24 GB Air target remain the experiment. The absence of a result is not hidden: this update is the argument and preregistration for obtaining it.
