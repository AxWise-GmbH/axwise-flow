Native engineering selection policy v1

These tools run in the current Goose conversation. Choose tools for the requested task; do not call every tool as a checklist.

- Prefer `ast_search` when the question concerns code structure, such as declarations or call shapes, rather than matching comments or strings. Use ordinary text/path search for filenames, literal text and unsupported syntax. AST accepts a real Tree-sitter query, not regex. Example for JavaScript declarations: {"path":"src","language":"javascript","query":"(function_declaration name: (identifier) @name)"}. For Python use `(function_definition name: (identifier) @name)`. A directory requires one explicit language. Supported grammars: rust, python, javascript, typescript, tsx, go, java, kotlin, swift, ruby. Inputs are saved workspace files, at most 2 MiB each, 256 files and 100 returned captures per call; inspect partial-scan results.
- Prefer `lsp_query` for semantic definitions, references, hover types and current-file diagnostics when a suitable server is configured or available. If a position is unknown, request `{"action":"symbols","path":"src/example.ts"}` first, then use its symbol selection range for definition/references/hover. Positions are zero-based lines and UTF-16 characters. Example after an edit: `{"action":"diagnostics","path":"src/example.ts"}`. These diagnostics supplement tests; missing or unversioned diagnostics do not establish correctness. On an unavailable server or unsupported action, report the limitation and use an appropriate local alternative.
- Before changing a supported existing file, prefer `hashline_edit` with `{"action":"read","path":"src/example.ts"}` to obtain its current full SHA-256 and exact line anchors. Copy those values into the edit; do not invent hashes, reuse stale anchors, or overwrite through another tool to bypass a conflict. Re-read and reconcile after a stale-file error. Editing uses inclusive one-based line ranges; replacement text must preserve intended newlines. Native edits support existing regular UTF-8 files up to 1 MiB inside this workspace; symlink traversal and new-file creation are unsupported.
- Prefer `safe_edit_and_test` when an existing-file edit has a suitable bounded test command. Pass the path, expected_sha256, anchored edits and literal test_command argv, for example `["node","--test","tests/example.test.mjs"]` only when that test exists and fits the change. Never invent a passing check. The tool edits one file, runs the supplied command and conditionally rolls back on failure, timeout or cancellation. Inspect the test and rollback receipt, then repair in this same conversation. A passing receipt only covers the command that ran, not all requirements or an independent review.
- For interdependent multi-file changes where testing each intermediate edit would fail, use guarded `hashline_edit` edits for the existing files, then run the relevant checks once the changes are coherent. This is not an atomic multi-file transaction and the individual edits are unverified. Use ordinary write for new files and ordinary tools for unsupported operations, stating relevant limitations. Do not treat test failure as permission to silently bypass it.

Only use tools present in the current tool list. Tool availability does not expand the user's request, replace normal permissions or add a remote Jev review. Stay in the session workspace. Local test commands have normal approved command authority; this tool is not an OS sandbox.
