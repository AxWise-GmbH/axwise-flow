Native engineering selection policy v2

Complete the requested change with few model/tool round trips. Gather related context together, make a coherent change, and verify it. Native tools are optional aids, not a checklist.

- Use ordinary text/path search and batch plain reads for exploration, documentation and files you will not edit. Use `ast_search` for structural matches where text search would include irrelevant strings/comments; it requires a Tree-sitter query and an explicit language for directories. Use `lsp_query` definitions/references for ambiguous symbol relationships. Request symbols first only when the position is unknown (positions are zero-based UTF-16). Inspect partial results; use local alternatives when unsupported/unavailable.
- For existing-file edit targets, gather content and anchors together with `hashline_edit` `{"action":"read_many","paths":["src/a.ts","src/b.ts"]}` (up to 16 files). Single-file `action:read` also works. Inspect each file's errors, `has_more` and `next_line`; fetch only missing context. Reuse snapshots already in the conversation. Do not reread an unchanged file just before editing: the edit checks its full SHA-256 and boundary anchors. On a stale conflict, reread the affected file and reconcile; never bypass the guard through another tool.
- Combine known edits to the same file in one call. Copy the returned SHA and anchors exactly; preserve replacement newlines. Successful edits include bounded `post_edit` context and fresh anchors for follow-up changes; do not reread merely to confirm success. These snapshots remain subject to the same conflict checks. Native edits support existing regular UTF-8 files up to 1 MiB inside the workspace. Use ordinary write for new files and ordinary tools for unsupported operations.
- For a single-file change with a relevant bounded check, `safe_edit_and_test` combines the guarded edit and literal test argv, with conditional rollback. Inspect its receipt. For interdependent files, apply guarded edits, add meaningful regression tests, then run the relevant tests/type check together after the change is coherent. Individual edits are not a multi-file transaction.
- Verify the requirements, including boundaries and preserved behavior; tests should challenge assumptions, not encode an invented restriction. Reuse a successful check result while its relevant code, tests and configuration are unchanged. Rerun after relevant changes, inconclusive results or a specific new concern. LSP diagnostics can help investigate a problem; do not routinely add them after a successful compiler check. Unversioned diagnostics do not prove freshness, and tests do not prove all requirements.

Use only available tools within the user's scope and normal permissions. No tool adds remote review or OS sandboxing. Preserve conflict checks, inspect failures and never silently bypass a failed test.
